## 修复：后端再次无响应——启动器日志读线程不安全导致管道阻塞 (13:49)

### 现象（用户反馈）
“后端服务又出现异常了”。`/health` 与 `/` 均 30s 超时，但 8000 仍在监听；端口堆积大量 `ESTABLISHED`/`FIN_WAIT_2` 半开连接；进程低 CPU（UserModeTime≈2s）、仅 7 线程。

### 诊断（与上次不同根因）
- 运行进程 PID 300 = 启动器于 13:42 用 `stdout=PIPE, stderr=PIPE` 启动的 uvicorn（无 `--reload`，系统 Python 3.13）。
- 排除上次根因：代码里所有 `urlopen` 都已包在 `asyncio.to_thread` 内（to_thread 绝不阻塞事件循环）；`database.py` 为异步连接池；`scheduler` 仅凌晨 2 点跑；全量 Grep 无 `subprocess.run`/`requests`/`socket` 等同步阻塞。即**代码层找不到在事件循环线程的同步阻塞**。
- py-spy 在本环境只装了元数据、`py-spy.exe` 未落地，改用推理+复现验证。
- **真正根因在启动器（不在后端代码）**：`启动器.py` 的 `read_process_output` 在子线程里直接调用 `self.all_log_text.insert(...)`/`see(...)` 等 Tkinter 控件操作，而 **Tkinter 非线程安全**。一旦子线程操作 Tkinter 死锁/卡住，便停止 `readline()` drain 管道；后端（uvicorn）写 stdout/stderr（访问日志、异常堆栈）时，64KB 管道缓冲区被填满后 `write` 系统调用**阻塞在后端事件循环线程** → 整个事件循环挂起，`/health` 也超时，但端口仍监听。
- 此解释完美对应“上次前台终端启动不卡、本次启动器(PIPE)启动却卡”的差异。

### 修复 `启动器.py`
1. `read_process_output`：读线程只负责 `readline()`，并把 UI 更新用 `self.root.after(0, log_callback, decoded)` 切回主线程执行；读线程**永不碰 Tkinter**，保证管道持续被 drain，后端写 stdout 永不阻塞。
2. 新增 `_start_backend()`（抽出后端启动+日志线程）与 `_health_watchdog()` 自愈看门狗：每 15s 检查 `/health`，端口未监听或连续 2 次健康检查失败即 `kill_process_on_port(8000)` 并自动重启后端。**避免再次出现“卡死需人工干预”**。

### 验证（实机）
- 杀 PID 300，用同命令后台重启后端（stdout 重定向文件，PID 10640），`/health` → 200。
- 复现 PIPE 模式压测（独立端口 8001）：安全读线程持续 drain + 30s 并发冲击（902 次 `/health` 探测）→ **HEALTH_FAILS=0/902**。

## 修复：启动器 `after(0)` 子线程仍触碰 Tcl 导致再次卡死 + 彻底改为 queue 方案 (14:21)

### 现象（用户反馈）
"在智慧大屏里边点击超期订单里边的订单ID后系统会卡死"。PID 15412（启动器于 14:21 启动的后端）事件循环全挂，`/health`/登录均超时，端口仍监听。

### 根因（比上次更深层）
- 复现脚本验证：**后端正常时 `getOrder`/`getOrderImages` 全部成功（~2s），请求本身不会卡死**。卡死与点击无关，纯粹是启动器 PIPE 模式又触发了同一类管道阻塞。
- **上次修复的缺陷**：上次把 `self.all_log_text.insert(...)` 改为 `self.root.after(0, log_callback, decoded)`——但 **`root.after()` 内部也会触碰 Tcl 解释器**，而 Tcl 不是线程安全的；在子线程调 `after()` 同样会与主线程竞争 Tcl 锁导致死锁，读线程卡住 → 管道堵 → 后端事件循环挂起。
- **正确方案：子线程绝对零 Tkinter 调用**——只把日志 `queue.put` 进线程安全队列，主线程用定时轮询消费队列并操作控件。

### 修复 `启动器.py`
1. 新增 `import queue`；`__init__` 中创建 `self.log_queue = Queue()` + 启动 `_poll_log_queue` 轮询（每 300ms）。
2. `read_process_output` 重写：签名从 `(process, callback, err_callback)` 改为 `(process, source)`；子线程只做 `readline()` + `log_queue.put((source, text))`，**零 Tkinter 接触**。
3. 新增 `_poll_log_queue()`：仅主线程执行，从队列取出 `(source, text)` 并调用对应 `add_backend_log/add_frontend_log`。
4. 后端/前端两处日志线程调用统一改 `args=(proc, 'backend')` / `args=(proc, 'frontend')`。
5. **看门狗线程** 4 处 `self.add_log(...)` 全部改为 `self.log_queue.put(('backend', ...))`（看门狗也是子线程，同样不能碰 Tkinter）。

### 验证
- 杀 PID 15412，命令行重启后端（PID 6828），`/health` → 200。
- 端到端压测脚本 `_verify_launcher_fix.py`（模拟修复后启动器行为：PIPE + 队列消费者）：独立端口 8001、并发 1000 次 `/health` + 模拟点击全部超期订单的 getOrder/getImages → **0 失败**。

### 经验
- **Tkinter/Tcl 的线程不安全范围比想象更广**：不仅是控件方法（insert/see/config），连 `root.after()` / `root.after_cancel()` 也触碰 Tcl 锁。子线程中任何涉及 `tk` 对象的调用都有死锁风险。
- 唯一安全的跨线程模式：**子线程只 `queue.put` + 主线程轮询消费**。

## 诊断：前后台"又出现异常 / 都连不上"（21:54）

### 现象
用户反馈前后台都连不上/异常。实时探测时端口一度 200，但 python 进程显示后端 PID 从 20492（本轮手动启动的 uvicorn）变为 12908（启动器拉起的），说明后端曾死掉并被启动器看门狗重启。

### 根因（读 启动器.py 确认）
- 启动器**独占并管理 8000/5173 端口**。关键逻辑：
  - `kill_process_on_port(8000)`（L46-59）：杀掉 8000 端口上**所有**进程，不只是它自己的子进程。
  - 启动逻辑（L1029-1036）：启动后端前若发现 8000 被占，先 `kill_process_on_port(8000)`。
  - 看门狗 `_health_watchdog`（L977-1002）：/health 连续失败 2 次即 `kill_process_on_port(8000)` 并重启。
- 本轮我手动起了后端 20492 与启动器并存 → 启动器一旦触发启动/看门狗逻辑，会杀掉 20492 并起自己的 12908；切换窗口内后端（及依赖其后端的页面体验）不可达，即用户看到的"异常"。
- 佐证：`backend_run.log` 只有一次启动横幅、其后全 200、**无 Traceback** → 20492 是被人/看门狗用信号杀掉，不是代码异常崩溃。新后端 12908 的输出进启动器 GUI 日志面板，不写 backend_run.log，故该文件停在 20492 的最后一行。
- Tkinter 线程死锁修复（queue 方案，L119-121/765-819）**仍在**，旧死锁根因已消除；本次复发是"端口归属冲突 + 看门狗激进"所致。

### 排查方法（已对用户演示）
1. 端口探针：`curl -s -o /dev/null -w "%{http_code}" http://localhost:8000/health` 与 `:5173`。
2. 进程：`tasklist | findstr python` + `netstat -ano | findstr ":8000"` 看 PID 是否变化。
3. 后端日志：`Get-Content backend_run.log -Wait`（tail -f）看 Traceback/500。
4. 浏览器 F12 → Console/Network 看前端侧报错（服务器日志看不到）。
5. 启动器 GUI 日志面板（看门狗重启记录在此）。

### 结论与待办
- **不要在启动器运行时手动起 uvicorn**——会与启动器抢端口被看门狗杀掉。要么全程交给启动器，要么停掉启动器单独手动起。
- 根治建议：改启动器只管理/重启它自己 `Popen` 的子进程 PID，不要无差别 `kill_process_on_port`；看门狗失败阈值放宽。待用户确认是否实施。
