1 项目概述

1.1 项目背景

搭建轻量化内网电商产销协同管理平台，打通销售端、工厂端、发货端、管理端（老板端）业务链路，替代线下表格管理，实现网店自主管理、订单统一录入、唯一追溯码+二维码溯源、工厂统一打印、发货全流程维护、图片凭证存档、操作全程留痕、销售提成可视化，提升订单流转与发货管控效率，确保数据安全可控。

1.2 业务目标

  1. 销售端：自主维护所属网店，标准化录入订单信息，上传产品图片，追踪个人订单状态，维护订单发货状态，查看个人订单提成金额及计算逻辑。
  2. 工厂端：查看所有状态下的订单（隐藏销售金额），拥有唯一二维码打印权限，配合订单流转，可上传图片告知生产任务，确保生产环节能全面对接所有订单需求。
  3. 发货端：查看自己关联操作的订单（隐藏销售金额），全权维护自己关联订单的发货状态、物流单号、物流公司信息、发货凭证，确保发货流程可追溯。
  4. 老板端：全数据管控，负责账号权限管理、数据备份、日志审计、销售端提成比例配置，掌握全局业务数据，可操作软件内所有功能。
  5. 财务模块：包含工资结算（提成结算）和账户提现功能，支持按发货时间统计提成、提现记录管理。

架构说明： - 客户端层：浏览器是日常操作入口；启动器是桌面管理端，负责拉起/停止前后端进程，其看门狗线程每 15 秒探测后端健康（端口 8000 + /health），后端崩溃自动重启（连续失败 5 次停止自愈）。 - 前端层：单页应用按业务模块拆分为 13 个模块目录，路由守卫统一做登录态与角色/数据权限校验；vite dev server 运行在 5173 端口。 - 后端层：FastAPI 按业务拆分为 21 个 API 路由文件，统一 JWT 鉴权 + require_role 角色校验 + 账号级数据权限拦截。 - 数据层：SQLite 单文件（免安装）；图片按订单/商品归档到本地目录，图片访问走鉴权路由。 - 外部系统：店铺级 API 配置（密钥 Fernet 加密存储）用于拉取平台订单写入临时表待审核。

4 核心字段定义

4.1 订单追溯码（order_id）生成规则

  • 生成格式：登录账号（username）+ 年月日（YYYYMMDD）+ 网店ID（shop_account）+平台订单号（platform_order_no）+ 6位随机数字
  • 示例：zhangsan20260424淘宝XX旗舰店P20260424001123456
  • 并发防重机制：
  • 系统启动时预生成1000个6位随机号存入内存队列
  • 新增订单时从队列取号拼接
  • 若重复则重试最多3次
  • 队列剩余≤100个时自动补充

4.2 商品唯一标识码（product_code）生成规则

  • 生成格式：PLU-{6位数字}（顺序编号，从1开始递增）
  • 示例：PLU-000001、PLU-000002、PLU-000100
  • 唯一性保证：基于数据库自增ID生成，保证唯一性
  • 生成时机：商品创建时自动生成，不可修改

4.3 提成计算公式

  • 公式：提成金额 = 销售金额 × 提成比例 ÷ 100
  • 取值范围：提成比例1-100（仅销售端账号）
  • 计算时机：订单创建时、编辑销售金额时自动计算

4.4 图片存储方案（方案A）

  • 临时目录：data/images/temp/
  • 正式目录：data/images/official/{order_id}/{layer}/（按追溯码+层级分目录）
  • 层级分类：
  • sales（销售端）：商品图片
  • factory（工厂端）：生产进度图片
  • shipping（发货端）：发货凭证图片
  • 清理机制：临时图片保留24小时
  • 完整性验证：使用MD5哈希值校验

4.5 生产状态定义

4.5.1 生产状态枚举

存储值 展示名称 说明
unproduce 未生产 新建订单默认状态，未开展任何生产作业
producing 生产中 工厂上传生产图片自动切换，代表车间正在生产
produced 生产完成 订单发货后自动锁定，生产流程永久结束，不存在返工、回退场景

4.5.2 手动修改权限&锁定规则

  • 手动修改权限：全部角色（boss、sales、factory、shipping）均可手动修改订单生产状态
  • 永久锁定机制：只要订单 shipping_status = shipped / virtual（已发货/虚拟发货），系统永久锁定生产状态为「生产完成」；任何人手动修改为「未生产/生产中」直接拦截，弹窗提示：订单已完成发货，生产流程结束，生产状态不可调整
  • 撤销发货锁定：即使后续手动撤销发货、将 shipping_status 改回 pending，生产状态依旧保持 produced，不允许人工下调，不支持返工

4.5.3 系统自动变更触发逻辑

触发1：工厂端上传factory层级生产图片 - 触发条件：上传用户角色为factory；图片层级 layer = factory（生产实拍图）；订单当前生产状态 ≠ producing - 执行动作：自动更新 produce_status = producing；同步更新 produce_status_update_at、produce_status_update_user = system-auto；写入操作日志，标记类型：系统自动-工厂上传生产图片；推送站内通知至订单创建销售、工厂、全部老板账号 - 防抖规则：订单已是「生产中」时，重复上传多张生产图片，不重复更新状态、不新增日志、不推送通知

触发2：发货端更新订单为已发货/虚拟发货 - 触发条件：接口更新订单 shipping_status 从 pending 变为 shipped / virtual - 执行动作：强制固定 produce_status = produced，不受前端传入参数影响；同步更新 produce_status_update_at、produce_status_update_user = system-auto；写入操作日志，标记类型：系统自动-订单完成发货，生产流程结束；推送站内通知至订单创建销售、工厂、全部老板账号；永久锁定，后续无论是否撤销发货，生产状态固定不变

12 数据清理管理

由原「日志清理管理」扩展升级而来，现统一纳管日志清理与站内信清理两类数据，入口整合在「系统设置」页面的标签页面板中。

12.1 功能概述

数据清理模块确保仅保留必要期限的运营数据，同时提供灵活的配置、预览、手动执行与定时自动执行能力。分为两个独立分区：

  • 日志清理：清理操作日志与登录日志（基于 created_at 时间戳）
  • 站内信清理：清理站内通知消息（基于 created_at 时间戳），默认最少保留 360 天

12.2 核心特性

  1. 基于时间戳的筛选：自动识别并删除超过保留期限的历史数据
  2. 可配置的保留期限：
  3. 日志保留天数：默认 730 天（2 年），最小 30 天，最大 3650 天
  4. 站内信保留天数：默认 360 天，最小 360 天（硬性约束，不可低于此值），最大 3650 天
  5. 删除前确认机制：手动清理前需二次确认，防止误操作
  6. 操作记录：所有清理操作记录在 log_cleanup_records 表，可追溯（cleanup_type 新增 notification 类型）
  7. 定时自动执行：
  8. 日志清理：每日凌晨 2:00
  9. 站内信清理：每日凌晨 2:10（与日志清理解耦，避免同一时刻资源争用）
  10. 手动触发接口：提供手动触发清理的 API 接口
  11. 失败重试机制：清理失败时自动重试，最多3次
  12. 异常告警：清理失败时记录错误日志

13 安全机制

  1. 密码存储：使用passlib库进行密码哈希，不存储明文
  2. Token认证：JWT令牌，有效期24小时
  3. 权限控制：后端接口层鉴权，前端按钮级权限控制
  4. 数据隔离：除boss/factory外，严格按创建人隔离数据
  5. 敏感数据过滤：factory/shipping角色不可查看金额相关信息
  6. 操作留痕：所有核心操作记录日志，不可删除篡改
  7. SQL注入防护：使用SQLAlchemy ORM进行参数化查询，防止SQL注入攻击
  8. 订单删除验证：删除订单时需要输入当前登录账号的密码，确保操作安全性

18.3 API接口规范

18.3.1 目录约束

  1. 所有后端请求接口全部归集至src/api/目录
  2. api目录固定分层：
  3. baseUrl.js：统一管理开发/测试/生产环境域名
  4. request.js：axios实例、请求/响应拦截器
  5. 业务api文件：按业务拆分（auth、user、order等）
  6. index.js：统一导出入口

18.3.2 编写规则

  1. 单一接口文件只对应一类业务
  2. 接口函数仅做网络请求，禁止混入业务逻辑
  3. 所有接口请求统一复用request.js导出的axios实例
  4. 请求地址、请求方式、参数严格封装在接口函数内

18.3.3 调用规则

  1. 页面、组件统一从@/api导入接口
  2. 鉴权Token、请求超时、统一报错提示全部由request拦截器处理
  3. 接口参数传递规范：GET请求使用params传参，POST请求使用data传参

18.4 模块拆分规范

18.4.1 模块划分标准

  1. 按业务域拆分独立模块，禁止按单一功能零散拆分
  2. 每个业务模块独立闭环，内部包含页面、私有组件、模块专属逻辑hooks
  3. 模块分层约束：
  4. 业务模块仅允许依赖api、utils、store公共目录
  5. 业务模块之间禁止直接import组件/方法
  6. 拆分粒度控制：单一业务域代码量低于200行不单独拆模块

18.4.2 模块依赖禁止项

  1. 禁止模块循环引用
  2. 禁止A模块直接import B模块内部页面、私有函数
  3. 禁止在模块组件内硬编码接口地址、环境域名、常量编码

18.5 业务逻辑层规范

18.5.1 职责划分

  • API层（src/api/）：仅负责网络请求，不包含业务逻辑
  • Service层（src/modules/*/services/）：负责业务逻辑、数据处理、计算等
  • View层（src/modules/*/views/）：负责UI展示和用户交互

18.5.2 Service层规范

  1. 所有业务逻辑统一放在模块的service层
  2. Service层函数负责数据计算、格式化、验证等业务逻辑
  3. Service层统一从@/api导入接口，禁止直接调用axios
  4. Service层函数必须包含错误处理和日志记录

18.6 维护约束

  1. 修改接口域名、请求拦截逻辑，仅修改api目录下对应文件
  2. 新增业务功能，优先在对应业务模块内新增代码
  3. 接口新增、修改仅改动对应业务api文件
  4. 删除废弃业务，直接删除完整业务模块文件夹

26 运维限制与已知约束（2026-08-13）

以下为启动器（启动器.py）在生产部署与日常使用中的硬性限制，部署前务必知悉。

26.1 自动数据库备份依赖启动器保持打开

  • 定时自动备份由启动器内的调度线程驱动。只有启动器程序保持打开（含最小化到系统托盘）时，定时备份才会执行。
  • 关闭 / 退出启动器后，备份调度线程随进程销毁，定时备份完全停止且不会补跑，用户无提示。
  • 备份设置页已增加醒目红色警告标签提醒此限制。
  • 无人值守部署：若需 7×24 定时备份，不要依赖启动器，应改用 Windows 任务计划程序 或 Linux cron 调用备份脚本。

26.2 看门狗仅自愈后端 API，前端不自愈

  • 启动器的健康检查看门狗只监控后端（端口 8000 / /health）。后端崩溃、端口消失、疑似死锁时，看门狗会自动重启后端。
  • 前端 vite 服务（端口 5173）不在看门狗监控范围内：前端进程崩溃或卡死时，界面仍显示「运行中」，浏览器实际白屏，看门狗不会自动重启前端，需人工重启启动器或前端。
  • 防雪崩保护：后端连续自愈重启达到 5 次上限后，看门狗停止自动重启并打印严重告警，等待人工排查；服务恢复正常后自动恢复自愈能力。

26.3 单实例锁

  • 启动器以 launcher.pid 文件做单实例锁（原子创建），专用端口 25999 仅作补充校验。
  • 进程被强制结束（任务管理器 / 强杀）后，下次启动会检测并清理陈旧 pid 文件，通常可立即重新打开，无需等待端口释放。
  • 若旧进程仍未真正退出（例如挂起未终止），则提示「启动器已在运行」，需先在任务管理器结束对应进程。

26.4 外部启动的前后端服务，启动器无法停止

  • 若 8000 / 5173 端口已被「启动器之外」的进程占用且健康，启动器会识别为「外部进程」并复用，状态标记为运行中。
  • 此时点击【停止系统】只能终止「本启动器管理的子进程」；外部进程不会被停止，界面仍显示运行中，需用户到任务管理器手动结束。
